## Что уже сделано и не должно регрессировать

### Уникальность имён и аватары

- Имена людей уникальны внутри партии, до 10 символов.
- Клавиатура вводит только заглавные буквы; искусственную проверку регистра убрали по замечанию пользователя.
- Крайние пробелы удаляются; повторные внутренние пробелы сводятся к одному.
- Пустая строка и строка из одних пробелов вызывают **«Имя не может быть пустым»**.
- Дубль вызывает **«Имя уже занято»**.
- A или B возвращают к редактированию, сохраняя текст и курсор; нажатие закрытия не должно вводить/стирать символ.
- Пустое имя не заменяется предложенным именем автоматически.
- Никаких автоматических цифровых суффиксов или обрезания имени для разрешения дубля.
- По кабелю авторитетная проверка выполняется на ведущей консоли. При дубле имя сохраняется за меньшим номером консоли, остальные редактируют.
- Исправление имени сохраняет соединение; остальные ждут. Старт заблокирован до разрешения конфликтов и завершения редактирования.
- START, которым ведущий подтвердил исправление своего имени, не должен одновременно запускать партию.
- Итоговые имена видны в комнате ожидания и синхронизированы.
- Дубли аватарок разрешены, включая стандартный «затылок» и портрет ИИ. Уникальность обеспечивает имя, аватар не является ID.
- Сейчас при двух людях зарезервированы имена всего выбранного пула ИИ, поскольку старый код меняет соперника между раундами. После закрепления одного ИИ необходимость резервировать весь пул нужно пересмотреть; отдельного решения сузить резерв только до фактического ИИ пока не было.

### Исправление шкатулок

- Ошибка: быстро закрытые шкатулки повторно рисовались поверх следующего результата, например «Переход хода» после сектора 0.
- Причина: `scene.chest_until` ещё не истёк, а отрисовка использовала его для любого `RESULT`.
- Исправление: `end_result()` завершает время показа (`scene.chest_until = scene.now`).
- Не заменять исправление локальной проверкой `result_reason` в рендере без анализа кабеля: это поле сейчас не передаётся в снимке, в отличие от `Scene`.
- Шкатулки в собственном результате награды остаются видимыми.

## Где искать реализацию

- `src/main.c`: `mp_stage()` с прежними названиями стадий, `Game`, структура `mp`, `prefs`, выбор режима/параметров, имена, ходы, начисление очков, `new_round`, `finish_round`, `begin_turn`, `final_records`, `end_result`, локальное редактирование кабельного имени.
- `src/scene.inc`: анимации, переходы сцен и рекламной паузы, ключи перерисовки.
- `src/presentation.inc`: интерфейс, клавиатура, нижняя панель, ожидание кабеля, отрисовка шкатулок.
- `src/link.inc`: GBA SIO, авторитетная ведущая консоль, проверяемый полный/дельта-снимок состояния, имена, локальные флаги исправления.
- `scripts/pack.py`: генерация ресурсов, CP866-строк и fingerprint сборки кабеля.
- `docs/multiplayer.md`: существующее поведение. Часть про 8 стадий, смену ИИ и победу в последней стадии станет устаревшей после реализации новой спецификации.
- `docs/reverse-hotseat.md`, `analysis/hotseat/decompiled.c`, `analysis/hotseat/listing.asm`: разбор DOS POLE2. Это источники об оригинале, а не требования сохранить отвергнутый классический режим.

### Важные особенности текущего кода

- Стабильные ID: `2` — первый игрок, `0` — второй, `1` — третий/ИИ.
- Панель имеет фиксированный порядок мест и не следует за перспективой сцены.
- Локально — два человека и ИИ либо три человека; по кабелю состав определяется подключёнными консолями.
- Ведущий считает правила и RNG; клиенты получают состояние. Новые очки, победы, стадия перестрелки, активный состав и итоги должны синхронизироваться.
- Сейчас мультиплеер жёстко идёт через 8 стадий, а победителем считается закрывший последнее слово.
- Сейчас ИИ может сменяться, получает случайные стартовые очки; это нужно убрать по новой спецификации.
- Сейчас `final_records()` может записывать результат победителя мультиплеера. Это нужно отключить, сохранив одиночный режим.
- Тесты читают символы ELF и отдельные смещения структур. При изменении layout обновить соответствующие fixtures, не принимать поломанные смещения за ошибку игровых правил.

## Сборка и проверки

Прочитать актуальный `AGENTS.md` и `docs/cloud-build.md` в целевой среде.

```bash
cd /workspace/wonderfield-gba
python3 scripts/build-cloud.py
```

Выход: `dist/pole 2.0.gba`, `build/gba/pole.gba`, `pole.elf`, `build-report.json`.
Используется Zig 0.13.0; в этой среде инструменты находятся в `/workspace/.tools/wonderfield`.
В новой среде наличие tools, исходных DOS-ресурсов и эмулятора нужно проверить, а не предполагать.

Проверки, использованные в этой работе:

```bash
export MGBA_LIBRETRO="$PWD/work/mgba/mgba_libretro.so"
python3 scripts/test-player-names.py
python3 scripts/test-multiplayer.py
python3 scripts/test-avatars.py
python3 scripts/test-panel-name.py
python3 scripts/test-chest-transition.py
MGBA_BUILD="$PWD/work/mgba/build" python3 scripts/test-link.py
```

- `work/mgba` — временные зависимости текущей среды, не часть поставки и не гарантированы в новом чате.
- Кабельный harness собирается с определениями ABI из соответствующей CMake-сборки mGBA 0.10.5; `test-link.py` умеет выбирать `--consoles` и `--scenario`.
- Кабель проверялся несколькими ядрами mGBA с тестовой моделью SIO. Проверки на физическом GBA Game Link Cable не выполнялись.
- Регрессионные отчёты: `docs/verification/player-names-tests.json`, `docs/verification/chest-transition-tests.json`. У отчётов есть SHA соответствующего ROM; не выдавать старый прогон за проверку нового кода.

Для новых правил нужны проверки результатов партии, банкрота в каждом режиме, ничьих/состава перестрелки, повторной перестрелки, досрочного финиша, одинакового учёта ИИ, отсутствия записи мультиплеера в SRAM, UI и кабельной синхронизации. Проверить границы 1 и 8 раундов, фиксацию промежуточного счёта ровно один раз и возврат выбывших в новом раунде.

## Передача изменённой сборки

Действующие инструкции проекта:

1. После изменения игры собрать актуальный ROM и выполнить подходящие проверки.
2. Обновить **существующие** `downloads/pole.2.0.gba` и `downloads/SHA256SUMS`.
3. Закоммитить и отправить код, тесты и ROM в **multiplayer**.
4. Не создавать отдельный GitHub Release без запроса пользователя.
5. Выдать прямую ссылку на ROM, привязанную к полному SHA коммита.
6. Скачать ROM по этой ссылке и сверить SHA-256 до передачи пользователю.
7. `CHANGELOG.MD` — только выпущенные изменения, не складывать туда планы и QA-отчёты.

Этот handoff сам по себе не требует менять игру или пересобирать ROM. Следующий чат должен сначала сверить состояние репозитория, затем реализовывать согласованную спецификацию по поручению пользователя.
